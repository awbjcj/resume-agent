  Root cause

  The failure is not a bug in your canonicalization or token data — it's the
  theming pass rejecting normal LLM output and aborting the whole run.

  The data flow (refresh_clusters, services/match_gap.py:104):

  collect tokens → dedup() → canonical_tokens (a set)
                → themer(canonical_tokens)  ← fails here
                → _validated_themes(...)

  themer is wired to build_skill_themer() (router match_gap.py:70). That closure
  does:

  themes

  themes_to_pairs demands an exact partition: every canonical token in exactly 
  one theme. When the LLM puts weaviate in two themes, canonicalize.py:90
  raises:

  That exception propagates straight out of themer(canonical_tokens), so
  refresh_clusters aborts, calls reporter.done(error=...), and re-raises — the
  run fails.

  Why weaviate, and why always

  1. weaviate is a vector database — it legitimately fits multiple themes the
  model invents (e.g. Data and Databases, or Data and AI/ML). Asking a model for
  a hard partition of inherently multi-category tokens is exactly the case it
  gets wrong.
  2. The cheap themer model is near-deterministic (low/zero temperature), so for
  your specific token set it makes the same misclassification every run →
  "always failed."

  llm_runner.acall. themes_to_pairs runs after runner.run() returns, outside the
  retry scope — so a duplicate-token response is a hard, un-retried failure.
