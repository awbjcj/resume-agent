  ---
  Design: Profile Corpus, Evidence-Linked Skills & Skill/Experience Matrix

  1. Source corpus & registry. data/profile/sources/ stores ingested documents;
  a manifest (sources.json) tracks doc id, filename, sha256, added-at, and one
  primary flag (your canonical resume). read_resume_text generalizes to
  read_document_text supporting .pdf, .docx, .txt, .md (plain read), and .pptx
  (new dep python-pptx; slide text frames + speaker notes). CLI: profile 
  add/remove/sources/build.

  2. Per-doc extraction, cached. Each document is independently extracted into a
  ProfileFacts-shaped fragment (data/profile/fragments/{doc_id}.json), cached
  by content hash + prompt version — adding doc #7 re-extracts only doc #7. The
  existing "never infer" extractor instructions stay for this pass.

  3. Inference pass (new, second stage). After literal extraction, an inference
  agent reads the merged facts and derives skills — including soft skills — each
  with inferred=true, evidence_fact_ids pointing at literal bullets, and a
  category (hard/soft/domain). Model changes: Skill.inferred,
  Skill.evidence_fact_ids, Skill.category; FactItem.source_ref (doc id).
  Bullets, dates, titles, metrics are never inferred.
  → Flagged sub-decision: may an evidence-backed inferred hard skill (e.g. "REST
  APIs" inferred from an API-building bullet) appear in the rendered skills
  section? I recommend yes — the fact-check gate is taught that an inferred
  skill with valid evidence ids is legitimate provenance. Soft skills stay out
  of the skills section per your earlier answer.

  4. Merge. Deterministic entity keys (experience: normalized company +
  title/date overlap; projects: normalized name, as today; education:
  institution + degree). Bullets union with a cheap-LLM near-duplicate collapse.
  Scalar conflicts: primary document wins, others fill gaps; conflicts printed
  in the build report. Fact ids become deterministic (derived from doc id +
  entity key + content) so unchanged facts keep ids across rebuilds and existing
  tailored resumes' provenance survives.

  5. Matrix. data/profile/matrix.json, regenerated from facts — never
  hand-edited. Row: canonical skill → aliases, category, inferred?,
  evidence_fact_ids, strength (evidence count × recency), last_used. Overrides
  (data/profile/overrides.yaml: ban token / force / forbid alias / recategorize)
  apply last and survive rebuilds.

  6. One canonical vocabulary, two match tiers. The existing ClusterMap
  canonicalizer refresh also ingests profile/matrix tokens, giving one shared
  alias space. Equivalent (same canonical) = covered; same theme = adjacent;
  else gap. Consumers: match_gap/demand graph go tri-state; fit scoring gives
  partial credit for adjacent; match_plan prompt gains a MATRIX section with
  explicit rules — adjacent skills argue transferability but are never claimed
  verbatim; soft-skill requirements are satisfied by selecting bullets that 
  demonstrate them and echoing JD vocabulary in the summary.

  7. Demand side. Strengthen the JD-criteria extraction prompt to reliably
  capture soft requirements into must/nice lists (no schema change, no
  re-extraction of old jobs).

  8. Testing & scope. Fully offline: faked agents, tiny fixture docs (incl. a
  minimal pptx), deterministic merge/matrix/override tests. Out of scope: web
  Profile page (phase-2 spec), embeddings, Gmail/LinkedIn sources.
